In November 2026, Microsoft took **Database Hub in Microsoft Fabric** to General Availability while setting an April 30, 2027 shutdown date for [Azure SQL Database Watcher](/blog/azure-sql-database-watcher-retirement/). Since then, several teams migrating off Database Watcher have asked me the same practical question: should we move database monitoring into Fabric Database Hub, or stream into our own Azure Data Explorer (ADX) cluster with [Culprit SQL](https://culpritsql.com)?

The honest answer depends on two things: whether your company already pays for large Fabric capacities, and whether you need root-cause execution-plan forensics across more than just Microsoft SQL.

<Callout title="When you should just use Microsoft Database Hub" tone="blue">

## Where the "$0" Database Hub story changes in production

Database Hub's entry screen has no per-database fee. That is genuinely nice for spotting an idle Elastic Pool or checking fleet versions across subscriptions.

The cost structure shifts as soon as on-call engineers try to wire it into real incident response:

1. **Alerting, retention, and AI burn Fabric Capacity Units (CUs).** Routing telemetry into a custom Fabric Eventhouse for longer KQL retention, setting up Data Activator alert rules, or asking Copilot / Database Agents to investigate an anomaly consumes paid Fabric capacity (F2 starts around `$263/month` pay-as-you-go; production multi-team capacities routinely run F8 to F64 at `$1,050` to `$8,400+/month`).
2. **The Power BI Pro viewer cliff below F64.** Sharing custom Fabric reports and dashboards across engineering without buying an F64 capacity requires a Power BI Pro license (`~$10 to $14/user/month`) for every developer who clicks an incident link in Slack.
3. **Single-vendor blind spots.** Almost every backend org I work with runs Azure SQL alongside Azure Database for PostgreSQL, Amazon RDS, MySQL, or YugabyteDB. Putting SQL Server in Fabric while Postgres lives in Grafana or Datadog splits on-call runbooks in half.

## What a CPU chart misses during a real regression

Cost is half the decision. Diagnostic depth is the other half.

Portal dashboards are good at showing that `billing-prod` spiked from 18% to 85% CPU at 14:10 UTC and that `SOS_SCHEDULER_YIELD` + `TEMPDB` writes jumped. They still leave an engineer staring at query IDs trying to figure out *why* a query that ran in `4 ms` all morning suddenly takes `412 ms`.

When Culprit's collector detects a regression window or memory-grant episode, it seals the native `.sqlplan` XML in private Blob Storage and runs a pure Rust diff before writing to `CulpritChangesV1`. ## How teams keep zero-trust production safety

A reasonable objection to running your own collector container is: *"How do I know a background collector won't hammer a struggling database?"*

We designed every collector source around [strict evidence and safety rules](/blog/why-database-monitors-cry-wolf-seven-evidence-rules/):

- **Source-verified `BuiltinSafety` envelopes:** Unattended 24/7 recipes run with `OPTION (MAXDOP 1)`, bounded `TOP (@P1)` row caps, byte ceilings, `1,000 ms` statement timeouts, and SHA-256 template verification. Broad physical page-header scans (`sys.dm_db_page_info` across all waiters) or full plan-cache sweeps stay off unless explicitly approved; active page-latch incidents inspect only the single contended page (`max_snapshot_rows = 1`).
- **Zero-query synthesis:** Diagnosis (`CulpritIncidentsV1`, `CulpritFindingsV1`, `CulpritChangesV1`) runs in Rust over local sealed captures *before* warehouse upload. Synthesizing findings sends **zero** extra SQL queries to your database.
- **Source-free web & MCP reads:** Both [`culprit-archive-web`](/blog/database-fleet-dashboard-adx-without-grafana-enterprise/) and warehouse [MCP tools](/blog/database-mcp-server-autonomous-verified-index-prs/) compile without database drivers (`dev/check-boundaries.py` enforces this in CI). A browser viewer or coding agent literally cannot open a connection to your production SQL Server.
