Microsoft retired Azure Data Studio on February 28, 2026. If you work on Windows and spend most of your day administering SQL Server instances, SSMS 21 is still the right tool for backups, Availability Groups, and Extended Events setup. And if you just need to connect and run T-SQL queries inside an editor, Microsoft's `mssql` extension for VS Code covers the basics.

Where things got awkward for me (working mostly on macOS, across services that mix Azure SQL, SQL Server, and PostgreSQL) was everything around execution plans, deadlocks, and query regressions.

## What actually broke in day-to-day query work

Three things kept coming up after switching away from Azure Data Studio:

1. **Opening `.sqlplan` and `.xdl` files from tickets or Slack.** Someone attaches a 2 MB `.sqlplan` or an Extended Events `.xdl` deadlock capture to an incident. On a Mac, you don't have SSMS. Reading raw Showplan XML in a text buffer (`<RelOp NodeId="7" PhysicalOp="Clustered Index Seek" Lookup="1">`) gets old fast, and dropping production query plans into a third-party website that uploads them to someone else's server is usually a non-starter for security reasons.
2. **Comparing Before and After plans.** Even in ADS and SSMS, tuning a slow query usually meant staring at two visual trees in separate tabs and trying to spot what moved. Did the join order flip, did an estimate drift by 100x because of a compiled parameter value, or did a Key Lookup disappear?
3. **Context-switching between SQL Server and PostgreSQL.** Most backend teams I work with don't run a single database engine anymore. One service is on Azure SQL, the next is on RDS PostgreSQL, and local tests hit SQLite. Having completely separate plan viewers and mental models for `.sqlplan` XML and `EXPLAIN (ANALYZE, BUFFERS)` wastes time when you just want to know which operator spent the time.

Over the past few months we pulled the plan parser, plan differ, and deadlock analyzer out of [Culprit SQL Studio](https://culpritsql.com) into standalone Rust + WebAssembly packages so they run in VS Code, in a browser tab, and in the desktop app using the exact same logic.

## Reading `.xdl` deadlock captures without SSMS

Deadlocks had the exact same problem on macOS and Linux. SQL Server's XML deadlock report has everything you need (`<victim-list>`, `<process-list>`, `<inputbuf>`, `hobtid` key locks, lock modes), but reading a multi-process lock cycle out of raw XML under incident pressure is error-prone.

## How my setup looks now

Depending on what I am doing, I use one of three entry points, all backed by the same Rust parser:

| When I need to... | What I use |
| :--- | :--- |
| Open `.sqlplan`, `.explain.json`, or `.xdl` files in a repo, compare two plan files in Explorer, or catch risky SQL migrations while coding | **[Culprit SQL for VS Code / Cursor](https://marketplace.visualstudio.com/items?itemName=culpritsql.culprit-sql)** (`culpritsql.culprit-sql`, also on Open VSX). Double-clicking a plan or `.xdl` file opens the viewer directly, `Cmd+Shift+E` opens a scratch Studio tab, and `.sql` / TypeScript `sql` templates get inline warnings for blocking `CREATE INDEX` or missing `WHERE` clauses. |
| Look at a plan from Slack or send a redacted link to a teammate | **[explain.culpritsql.com](https://explain.culpritsql.com)**. Runs 100% locally in WebAssembly inside your browser tab (nothing is uploaded). Clicking **Share Link** scrubs SQL string and numeric literals by default, compresses the plan with `deflate-raw`, and puts it in the `#s=z1...` URL hash. |
| Connect to Azure SQL, SQL Server, PostgreSQL, or MySQL to find *which* queries are slow in the first place | **[Culprit SQL Studio](https://culpritsql.com)** (native macOS, Linux, and Windows app + CLI). It imports saved connections directly from Azure Data Studio's config file, signs in to Azure SQL using your existing `az login` Entra session, reads Query Store / DMVs / `pg_stat_statements` read-only, and ranks findings by share of database time. |

One small bonus if you use Claude Code, Cursor, or Codex: running `culprit mcp` exposes 27 read-only tools over your saved connections, so your coding agent can inspect Query Store regressions, pull execution plans, or test hypothetical indexes (`--with-index` via HypoPG on Postgres) without ever seeing raw database credentials.
