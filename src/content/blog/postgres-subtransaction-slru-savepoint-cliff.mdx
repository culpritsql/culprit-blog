One of the nastiest outages on Amazon RDS for PostgreSQL or Aurora PostgreSQL starts without a slow query deploy or a traffic spike. Average CPU sits at 25% all week, then jumps to 98% in thirty seconds while thousands of fast primary-key and index lookups stall on `LWLock:SubtransSLRU` (or `SubtransControlLock` on older versions).

Killing the slowest `SELECT` queries does nothing, because those `SELECT` queries are victims.

## Why 65 savepoints change how every reader checks MVCC visibility

Every `SAVEPOINT` (and every `BEGIN ... EXCEPTION WHEN ... END` block in PL/pgSQL) allocates a child transaction ID (`subxid`) when it modifies state. To keep MVCC snapshot checks fast, PostgreSQL stores up to **64** subtransaction XIDs directly inside each backend's `PGPROC` structure in shared memory (`PGPROC_MAX_CACHED_SUBXIDS`).

As long as every active session stays at or below 64 subtransactions, `XidInMVCCSnapshot()` scans those small in-memory arrays without touching `pg_subtrans` pages.

The cliff arrives when two conditions overlap:

1. **At least one backend overflows 64 subtransactions** inside a single parent transaction (setting `subxids.overflowed = true` in `ProcArray`).
2. **A long-running transaction or hot-standby feedback pin holds the global `xmin` horizon back** (for example, an analytics export, an `idle in transaction` session, or `hot_standby_feedback = on` with a slow replica query).

Once `ProcArray` contains an overflowed snapshot and `TransactionIdPrecedes(xid, TransactionXmin)` is false for newly written tuples, **every concurrent reader** inspecting those tuples has to look up their top-level parent XID in `pg_subtrans` SLRU buffers. Under 200 concurrent connections, cache lines bounce across cores and SLRU page replacements serialize readers behind `SubtransSLRU`.

## Catching both halves of the incident in SQL

During a live stall on PostgreSQL or AWS RDS, run one read-only diagnostic query against `pg_stat_activity` to separate the **wait victims** from the **horizon pin** and **savepoint writer**:

```sql
/* culprit */
SELECT pid,
       usename,
       application_name,
       state,
       wait_event_type,
       wait_event,
       age(backend_xmin) AS xmin_age_xids,
       now() - xact_start AS xact_age,
       left(query, 120) AS current_sql
FROM pg_stat_activity
WHERE pid <> pg_backend_pid()
  AND (xact_start IS NOT NULL OR wait_event IS NOT NULL)
ORDER BY coalesce(age(backend_xmin), age(backend_xid), 0) DESC,
         xact_start ASC NULLS LAST
LIMIT 25;
```

Look at two distinct rows in that output:

- **The horizon holder** sits at the top with a large `xact_age` or `xmin_age_xids` (often `state = 'idle in transaction'` or a 20-minute reporting `SELECT`).
- **The victim herd** sits stacked on `wait_event_type = 'LWLock'` and `wait_event IN ('SubtransSLRU', 'SubtransBuffer', 'SubtransControlLock', 'MultiXactOffsetSLRU')`.

## Three code patterns that silently mint thousands of savepoints

Developers almost never write raw `SAVEPOINT sp_42` in application code. Savepoint storms come from ORM helpers nested inside loops:

1. **Django `with transaction.atomic():` inside a `for` loop** when an outer request or Celery task already opened `atomic()`. The outer block starts `BEGIN`; every inner iteration emits `SAVEPOINT` and `RELEASE SAVEPOINT`.
2. **ActiveRecord `Model.transaction(requires_new: true)`** or Sequel `db.transaction(savepoint: true)` called per imported CSV row to catch `RecordNotUnique`.
3. **PL/pgSQL `BEGIN ... EXCEPTION WHEN unique_violation THEN ... END;`** inside a `FOR` loop over thousands of items. Every entry into an `EXCEPTION` block allocates a subtransaction.

## Fixing the writer and capping the blast radius

Replace exception-driven savepoint loops with single-statement conflict handling:

```sql
-- Zero savepoints, zero subxids, one round-trip for 1,000 rows:
INSERT INTO public.payment_attempts (merchant_id, idempotency_key, amount_cents, state)
SELECT * FROM unnest($1::bigint[], $2::text[], $3::bigint[], $4::text[])
ON CONFLICT (merchant_id, idempotency_key)
DO UPDATE SET state = EXCLUDED.state,
              updated_at = now()
WHERE public.payment_attempts.state <> 'settled';
```

Then enforce two server-level guardrails (via RDS Parameter Group or `ALTER DATABASE`) so one forgotten transaction cannot pin the MVCC horizon for twenty minutes:

```sql
ALTER DATABASE payments SET idle_in_transaction_session_timeout = '30s';
ALTER DATABASE payments SET statement_timeout = '60s'; -- override per reporting role if needed
```
