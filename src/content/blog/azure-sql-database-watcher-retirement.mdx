## Why losing the ADX pipeline stings

Microsoft's migration guide points to **Database Hub in Microsoft Fabric**. If your company already bought Fabric capacities and wants a managed portal covering Azure SQL, SQL Server on VMs, and Azure Arc, that direction makes sense.

  </p>
</Callout>

For teams who chose Database Watcher specifically **because it wrote into their own ADX cluster**, moving into Fabric creates three headaches:

- **Split observability.** When application logs, Kubernetes events, and database waits sit in the same Kusto cluster, you have one query language (KQL), one Terraform stack, and one Azure Monitor / Grafana alert path.
- **Orphaned ADX billing.** When Database Watcher stops on April 30, 2027, Azure does not pause or delete the ADX cluster you provisioned for it.
- **Single-vendor coverage.** Production backends rarely stop at Azure SQL. Most teams also run PostgreSQL, MySQL, MariaDB, YugabyteDB, or self-managed SQL Server right alongside it.

## Why raw DMV tables struggle at 2 AM

While building [Culprit SQL](https://culpritsql.com), I kept running into a deeper issue with raw DMV pipelines: **metrics tell you something hurts, not which query broke it.**

Getting paged at 2 AM with *"CPU > 90% on `orders-prod`"* or *"LCK_M_X wait spike"* still forces the on-call engineer to write five KQL joins half-asleep to figure out:

1. Did a query flip execution plans after statistics updated, or did request volume spike?
2. Is checkout queued behind an `idle in transaction` session holding a row lock while waiting on an HTTP call?
3. Did alerts stay quiet because the database is healthy, or because the collector lost `VIEW DATABASE PERFORMANCE STATE`?

## Wiring KQL alerts that include the culprit

Instead of maintaining fragile multi-table joins in every alert rule, you can query `CulpritIncidentsV1` directly from an Azure Monitor Scheduled Query Rule or Grafana:

```kql
CulpritIncidentsV1
| where UpdatedAt > ago(5m) and Status == "active" and Severity == "high"
| project StartedAt, DatabaseName, CulpritKind, Headline, CulpritSql, DeveloperAction
```

Or generate typed Kusto stored functions bound to your archive namespace (`culprit collect queries --config archive.json --name Prod ...`):

```kql
ProdNewIncidents("Orders production", ago(5m), now(), now())
```

<Callout title="Never confuse missing telemetry with a healthy database" tone="amber">
  <p>
    An empty result from an incident query should never silence a broken collector. Run a separate KQL check on <code>ProdStatus</code> so permission drops or stalled ingestion page separately from database incidents.
  </p>
</Callout>

```kql
ProdStatus("Orders production", now(), 30m)
| where State != "observed" or not(InputReadComplete) or array_length(ContextIssues) > 0
```

## Replaying an incident without touching production

When an alert fires, neither you nor a coding agent needs to open a live connection to the production database. Using read-only ADX and Blob credentials, pull the exact 10-minute capture window from the CLI:

```sh
culprit resources --config evidence.json --json
culprit incident "Orders production" --around 2026-11-21T02:15:00Z --config evidence.json
```

Or open **Telemetry archives** in the [Culprit SQL Studio](https://culpritsql.com) desktop app (or host [`culprit-archive-web`](/blog/database-fleet-dashboard-adx-without-grafana-enterprise/) for zero-seat browser triage) to step through the captured queries, execution plans, and blocking chains offline.
