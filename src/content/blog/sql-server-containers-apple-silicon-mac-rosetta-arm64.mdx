A rumor keeps making the rounds in backend Slack channels: *"Apple is removing Rosetta 2 in macOS 28, so you won't be able to run SQL Server Docker containers on an Apple Silicon Mac anymore."*

Because we test [Culprit SQL](https://culpritsql.com) daily against disposable SQL Server, PostgreSQL, MySQL, and YugabyteDB containers on M-series Macs, I dug into Apple's Virtualization documentation and Microsoft's container roadmap to separate what is actually retiring from what got conflated on social media.

The short version: **Linux containers are fine, Azure SQL Edge is dead, and you finally have a real native ARM64 option.**

## Myth vs. reality: macOS Rosetta 2 vs. `RosettaLinux`

The confusion comes from Apple using the name "Rosetta" for two different layers:

1. **macOS application Rosetta 2 (retiring after macOS 27):** Translates Intel (`x86_64`) Mach-O macOS apps and frameworks (AppKit, Cocoa, Intel plugins, printer drivers). Apple confirmed macOS 27 is the final release with full general-purpose support, shrinking in macOS 28 to a narrow subset for legacy unmaintained Intel games.
2. **Rosetta for Linux VMs (`VZLinuxRosettaDirectoryShare`):** When you run an `amd64` container in Docker Desktop, OrbStack, Podman, or Apple's open-source `container` CLI, macOS boots a **native ARM64 Linux kernel VM**. Inside that Linux guest, `/Library/Apple/usr/libexec/oah/RosettaLinux` is mounted over `virtiofs` and registered with `binfmt_misc` to translate `x86_64` Linux ELF binaries directly to ARM64 instructions. It does not touch macOS desktop frameworks at all.

## What actually broke SQL Server on Macs in 2025-2026

Even though Linux binary translation stays alive, Mac developers hit two very real roadblocks over the past year:

- **Azure SQL Edge retired on September 30, 2025.** For years, `mcr.microsoft.com/azure-sql-edge` was every Mac developer's favorite workaround because it shipped a fast `linux/arm64` build. Once Microsoft retired it and removed support, teams were pushed back toward `mcr.microsoft.com/mssql/server` (`amd64`-only).
- **The SQL Server 2025 AVX assertion crash.** When SQL Server 2025 leaned harder into `x86` Advanced Vector Extensions (AVX), running `amd64` containers under Rosetta translation on certain macOS 26 ("Tahoe") and Docker combinations crashed immediately at boot with:

```text
sqlservr: assertion failed [x86_avx_state_ptr->xsave_header.xfeatures == kSupportedXFeatureBits]
```

That crash had nothing to do with Apple banning containers; it happened because SQL Server's startup check inspected simulated CPU `XSAVE` vector state flags under `x86_64` translation.

## Option 1: Native ARM64 via the Azure SQL Database container (Recommended for dev)

If your production target is Azure SQL Database (or your integration tests just need T-SQL, Query Store, rowstore/columnstore indexes, and JSON/vector types), stop emulating `x86_64`. Use Microsoft's **Azure SQL Database local container** (`mcr.microsoft.com/mssql/azure-sql-db-server`), which ships a native `linux/arm64` manifest:

```sh
docker run -d \
  --name sql-arm \
  -e ACCEPT_EULA=Y \
  -e MSSQL_SA_PASSWORD='LocalDev-Password-2026!' \
  -p 127.0.0.1:14333:1433 \
  mcr.microsoft.com/mssql/azure-sql-db-server:latest
```

Cold boot drops from 20+ seconds under emulation to a couple of seconds, fan noise disappears, and memory-mapping / AVX translation bugs vanish because every instruction is native ARM64.

## Option 2: Boxed `mssql/server:2022-latest` when you need instance-level features

When we test Culprit's boxed SQL Server collectors (SQL Server Agent jobs, `msdb` suspect pages, instance-level `system_health` Extended Events `.xel` files, or Availability Group redo queues), we still spin up `mcr.microsoft.com/mssql/server:2022-latest` with explicit `--platform linux/amd64` and a 2 GB to 4 GB memory cap:

```sh
docker run -d \
  --name sql2022-amd64 \
  --platform linux/amd64 \
  -e ACCEPT_EULA=Y \
  -e MSSQL_SA_PASSWORD='LocalDev-Password-2026!' \
  -e MSSQL_MEMORY_LIMIT_MB=2048 \
  -p 127.0.0.1:14334:1433 \
  mcr.microsoft.com/mssql/server:2022-latest
```

## Inspecting plans and slow queries on macOS now that Azure Data Studio is gone

Running the database container is half the local workflow; the other half is having a fast native macOS client now that Azure Data Studio is retired too.

I wrote up [my full post-Azure Data Studio macOS and VS Code workflow here](/blog/after-azure-data-studio/). If you want to scan that local container right from your Mac terminal to spot implicit conversions, missing indexes, or Key Lookups while developing:

```sh
culprit conn add local-sql --env local --password-env MSSQL_SA_PASSWORD \
  --url 'mssql://sa@127.0.0.1:14333/app_dev?encrypt=false&trustServerCertificate=true'

MSSQL_SA_PASSWORD='LocalDev-Password-2026!' culprit scan local-sql
```

Both the CLI and [Culprit SQL Studio](https://culpritsql.com) ship as native Universal / Apple Silicon binaries (`arm64`) under the MIT license, and [wire directly into Claude Code or Cursor via MCP](/blog/database-mcp-server-autonomous-verified-index-prs/) so you catch bad queries locally before they ever hit Azure.
