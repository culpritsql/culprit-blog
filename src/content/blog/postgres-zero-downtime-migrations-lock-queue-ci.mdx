Almost every backend team learns PostgreSQL's lock-queue rule the hard way at least once.

An engineer writes `ALTER TABLE orders ADD COLUMN retry_count integer;` in a migration, tests it against a staging copy with 500,000 rows, sees it finish in `9 ms` (no table rewrite in modern PostgreSQL), and merges the pull request.

During deploy, production connection pools hit 100% saturation and health checks fail across every API pod.

## The `ACCESS EXCLUSIVE` lock-queue sandwich

The migration itself did not rewrite `orders`. What took down the API was **lock-queue fairness**.

1. At `14:00:01`, an internal dashboard or background job starts a `SELECT` over `orders` (`ACCESS SHARE` lock) that takes `9 seconds`.
2. At `14:00:02`, the deploy job runs `ALTER TABLE orders ADD COLUMN ...`, requesting `ACCESS EXCLUSIVE`. Because `ACCESS SHARE` is currently held by the dashboard query, `ALTER TABLE` enters the wait queue.
3. At `14:00:02.005`, 400 API requests/second run `SELECT * FROM orders WHERE id = $1`. To prevent writer starvation, PostgreSQL queues every new `ACCESS SHARE` request **behind** the waiting `ACCESS EXCLUSIVE` DDL session.

For the next eight seconds, zero reads or writes on `orders` return.

## Four rewrites that keep hot PostgreSQL tables online

### 1. Always bound DDL wait time with `lock_timeout`

Never let a migration wait indefinitely in the lock queue. Prefixing DDL with `SET LOCAL lock_timeout = '2s'` (or session `SET lock_timeout = '2s'`) fails the migration cleanly if a long reader is active so your deploy runner can retry seconds later without piling up application connections:

```sql
SET lock_timeout = '2s';
ALTER TABLE public.orders ADD COLUMN retry_count integer;
RESET lock_timeout;
```

### 2. Build and drop indexes `CONCURRENTLY` outside transaction blocks

Standard `CREATE INDEX` takes a `SHARE` lock, blocking every `INSERT`, `UPDATE`, and `DELETE` for the entire index build. `CREATE INDEX CONCURRENTLY` uses `SHARE UPDATE EXCLUSIVE` over two table scans so reads and writes continue uninterrupted, provided your migration runner disables its automatic `BEGIN ... COMMIT` wrapper (`MIG002`):

```sql
-- disable_ddl_transaction! (Rails) / atomic = False (Django) / -- migrate:no-transaction
CREATE INDEX CONCURRENTLY IF NOT EXISTS orders_customer_status_idx
  ON public.orders (customer_id, status);
```

### 3. Add `FOREIGN KEY` and `CHECK` constraints in two phases (`NOT VALID`)

`ALTER TABLE child ADD CONSTRAINT ... FOREIGN KEY ...` validates every existing row while holding `SHARE ROW EXCLUSIVE`, blocking writes on both tables. Splitting creation from validation downgrades the full scan to `SHARE UPDATE EXCLUSIVE`:

```sql
SET lock_timeout = '2s';
ALTER TABLE public.webhook_deliveries
  ADD CONSTRAINT webhook_deliveries_workspace_fk
  FOREIGN KEY (workspace_id) REFERENCES public.workspaces (id)
  ON DELETE CASCADE NOT VALID;
RESET lock_timeout;

-- Scans existing rows under SHARE UPDATE EXCLUSIVE (concurrent reads & writes continue):
ALTER TABLE public.webhook_deliveries
  VALIDATE CONSTRAINT webhook_deliveries_workspace_fk;
```

### 4. Index referencing `FOREIGN KEY` columns (`MIG004`)

PostgreSQL automatically creates a unique index on `workspaces(id)`, **never** on `webhook_deliveries(workspace_id)`. The day a customer deletes a workspace or a retention job prunes expired accounts, `ON DELETE CASCADE` (or referential integrity verification) executes a full sequential scan across `webhook_deliveries` for every deleted parent row.

## Enforcing migration rules automatically in GitHub Actions

Code review catches unsafe DDL when a senior engineer happens to spot it; automated PR gates catch it every time. Drop [`culpritsql/culprit-ci`](https://github.com/culpritsql/culprit-ci) into `.github/workflows/sql-ci.yml`:

```yaml
name: SQL Migration Gate

on:
  pull_request:
    paths:
      - "migrations/**"
      - "db/migrate/**"

permissions:
  contents: read
  pull-requests: write
  security-events: write

jobs:
  lint-migrations:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Lint PostgreSQL migrations & emit SARIF
        id: sql-gate
        uses: culpritsql/culprit-ci@v0.5.11
        continue-on-error: true
        with:
          sql: "migrations/*.sql"
          engine: "postgres"
          fail-on: "high"
          sarif-file: "culprit.sarif"
          post-comment: "true"

      - name: Annotate PR diff via GitHub Code Scanning
        uses: github/codeql-action/upload-sarif@v3
        with:
          sarif_file: culprit.sarif

      - name: Enforce gate
        if: steps.sql-gate.outputs.passed != 'true'
        run: exit 1
```

Notice one detail that keeps developers from muting the linter: `@culpritsql/ci` tracks `CREATE TABLE <name>` statements within the same migration file. Indexing or altering a brand-new empty table created two lines earlier never triggers false `MIG001` or `MIG006` alarms.

When you also connect [Culprit SQL Studio](https://culpritsql.com) or [MCP coding agents](/blog/database-mcp-server-autonomous-verified-index-prs/), `culprit lint-sql prod-snapshot.json --file migrations/ --write` weights every migration against your real table row counts, write rates, and recorded query workload, and rewrites supported DDL into concurrent operations automatically.
